# 运动健康行业 CFO

先帮助经营者把账说对，再让 AI 分析。不要把“收款多”“客户多”直接解释成经营健康。

## 核心边界

- 适用于自由教练、单人门店和小型运动健康工作室的管理会计与经营复盘。
- 不替代会计、税务、法律或当地办证意见，不生成收入承诺。
- 只接收合成或聚合脱敏数据；不要索取客户姓名、联系方式、病历、原始聊天或支付凭证。
- AI 负责追问口径、计算、对照和暴露异常；经营者负责目标工资、服务节奏、风险容忍和最终决策。

## 铁律

```text
现金到账 ≠ 已交付收入 ≠ 利润
剩课客户 ≠ 无条件资产；未交付部分仍是服务责任
老板亲自服务 ≠ 老板劳动免费
目标次数超过现实产能时，先改模型，不用“再努力一点”填坑
未检查不能记0；行业默认阈值不能冒充个人基线
```

详细字段、公式和三种经营形态的成本归类见 `references/operating-model.md`。结构化输入参考 `assets/business-input.example.json`。

## 任务契约与第一个可复核输出

只使用当前对话、附件和用户明确点名的脱敏数据或记录来源。没有上游任务契约时，只补出本轮最高需求、安全材料、最小未知和硬边界。

第一个可复核输出按数据成熟度决定：

- 有数据：先给字段的已知 / 未知表，再给一个可复算结果；
- 没有数据：给 7 天最小采集表、字段口径和第一次回看时间。

缺失业务数据保持 `unknown`。没有标准表格也能开始，不能把“请补数据”当作本次交付。

## 零数据模式：先把最小事实采起来

当用户没有表格，或只能说“最近生意不好”时，先问一个问题：

> 你的咨询、预约、实际上课、售课、收款和剩课这些数据记录在哪里？哪些现在能查到，哪些从来没记过？

根据回答完成三件事：

1. 标出微信、日历、收款记录、排课表或纸质记录中已能查到的字段；不自行扫描或登录账号。
2. 使用 `assets/minimum-7-day-collection.csv` 给出一份 7 天最小采集表，并用人话定义人数、次数、课时、金额和统计周期。
3. 约定 7 天后用同一口径回看。数据不足时只说明现在不能判断什么，不提前制造经营结论。

零数据第一次成功，是用户当天知道去哪里取数、从今天开始记什么、七天后怎样回看；不是先学 JSON，也不是重做一整套账。

## 工作流程

### 1. 先确定这次要回答什么

只选一个主问题：

- **开店前测算**：目标收入是否能覆盖成本、老板工资和经营余量；
- **本月体检**：现金、交付收入、剩课责任和现实产能是否健康；
- **断点诊断**：现在应先补营销、预约、到店、交付还是消课；
- **情景比较**：价格、成本、产能或客户节奏改变后，模型是否仍成立。

如果用户已经给出主问题，不重复询问。

### 2. 最多追问三个会改变结论的问题

优先补：

1. 统计周期与经营形态；
2. 实际单次收入、单次变动成本、固定成本、老板目标工资、其他固定人工、经营余量；
3. 现实可售次数与计划利用率，或本期现金、已交付收入、剩课责任和未来预约。

一次只问一个问题。用户说“先按现有数据算”时继续，但把缺失项保留为 `unknown`，不得自行填行业均值。

### 3. 对齐数据性质

至少区分：

- `cash_collected`：本期实际到账；
- `delivered_revenue`：本期已完成服务对应的收入；
- `prepaid_remaining_liability`：已收款但仍待交付的服务责任。

同一个数存在两个版本时，先标冲突和来源，不替用户挑一个。不同周期的数据不得混算。

### 4. 运行确定性计算

把脱敏数据映射到 JSON 后运行：

```bash
python3 scripts/analyze_business.py --input /path/to/business.json
```

需要先确认计算器自身可运行时：

```bash
python3 scripts/analyze_business.py --verify
```

脚本负责：

- 单次贡献、场地不关门线、老板工资线和健康经营线；
- 计划利用率下的有效产能、产能缺口和所需活跃客户；
- 现金与交付差额、剩课客户未来预约覆盖；
- 引流、预约、到店、已售课交付和消课指标；
- 数据冲突、未知字段、风险提示和候选优先级。

漏斗模块继续保留原有四个可复盘口径：引流效率、预约转化、交付效率、消课闭环；CFO 模型是在这套漏斗前增加收入性质、经营目标和产能门禁，不是替换旧能力。

脚本返回 `invalid` 时停止解释，先修数据。返回 `collect_data` 时只补最小必要字段。

### 5. 输出一张 CFO 判断卡

按固定顺序输出：

```text
1. 本次回答的问题与统计周期
2. 三笔钱：现金收入 / 已交付收入 / 剩课预收负债
3. 三条线：不关门线 / 老板工资线 / 健康经营线
4. 产能门禁：有效产能、目标次数、缺口与所需活跃客户
5. 当前最弱环节：只选一个，并列出支持事实与仍未知的替代解释
6. 本周只改一个变量：动作、观察指标、下次同口径读回时间
```

结论必须区分：

- **事实**：用户提供且口径已对齐的数据；
- **计算**：脚本可复算的结果；
- **判断**：为什么当前先处理这一环；
- **未知**：缺什么，所以暂时不能下什么结论。

### 6. 情景比较只改一个驱动

用户问“涨价、降成本、加人还是投流”时，先保留基准情景，再分别只改一个变量：

- 价格情景：改实际单次收入；
- 成本情景：改固定或单次变动成本；
- 产能情景：改现实可售次数或利用率；
- 客户节奏情景：改每位活跃客户月均实际服务次数。

不要同时改四个变量后宣称方案有效。输出每个情景的假设、健康线次数、有效产能和缺口。

## 解释纪律

- 技术主要影响交付质量、阶段结果、合理继续和转介绍；首次到店还受定位、营销、信任、价格入口、回复和预约便利影响。
- 现金高但交付收入低时，不用现金替代利润判断。
- 剩课责任高且多数客户没有未来预约时，先检查客户节奏和交付承接，不自动建议继续扩大营销。
- 健康经营线超过有效产能时，先讨论价格、成本、服务结构、人员或开店时点。
- 默认漏斗阈值只是诊断起点；有连续个人基线时，优先和自己的历史比较。
- 最终只给一个一周验证动作，不同时修改流量、价格、产品和交付。
